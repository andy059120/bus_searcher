# TDX 基礎會員的查詢策略

此設定依使用者提供的方案：每把金鑰每分鐘 5 次、每月 3 點。程式減少請求，不推算或保證月點數足夠；實際點數餘額與各資料服務計費仍以 TDX 會員中心為準。

## 使用流程

1. 點首頁上方搜尋列，輸入路線名稱；停頓 800 毫秒後一起查詢雙北，或按鍵盤搜尋立即送出。
2. 不必選城市；每個結果仍保留營運城市及 RouteUID，進入明細後只查該路線。
3. 明細沿用原本去返程分頁與左右滑動操作；到站時間與站名列在同一行，將進站以紅色標示。
4. 點站牌開啟底部選單，加入或移除常用站牌。切換方向與操作收藏不呼叫 API。
5. 下拉刷新或按右上更新取得到站資料；60 秒內直接使用快取。畫面顯示資料取得時間。
6. 達到頻率限制時顯示稍後重試，不排隊、不自動重試 429。

首次搜尋雙北並開啟路線需要 4 次資料請求（雙北搜尋 2 次、站序 1 次、到站 1 次），另加首次認證 1 次，保守計入每分鐘 5 次。相同查詢會共用快取；已有完整搜尋結果時，繼續縮小關鍵字可直接在本機篩選。一城市失敗時仍呈現另一城市的成功結果，並顯示未完成城市的錯誤。

## 限流與快取

- `TdxRequestLimiter`：在任意滾動 61 秒視窗最多送出 5 次，包含認證、失敗請求與 401 重試；多留 1 秒邊界。
- 認證與資料 API 共用同一個限流器。各頁面共用 `BusRepository`，合併相同且進行中的查詢。
- 收到 429 時至少冷卻 61 秒；`Retry-After` 若要求更久，依其秒數或 HTTP 日期延長，不會自動再次發出請求。
- 路線搜尋快取 1 小時、站序快取 24 小時、到站資料快取 60 秒。只快取成功解析的結果，包含有效的空清單。
- 最多保留 100 筆查詢快取，優先淘汰最久未使用的項目。
- 快取、限流紀錄與收藏均在記憶體中；重新啟動會清除。多裝置或重新啟動的用量仍由 TDX 統一限制，本機無法得知其他程式的流量。
- 公開散布且共用同一把金鑰時，需由後端集中限流與快取，才能管理跨裝置用量。

## 資料配對與顯示

改用 `StopOfRoute` 保留 RouteUID、SubRouteUID、Direction、StopUID 與 StopSequence。每個附屬路線及方向分開顯示，站序依 StopSequence 排序。

到站時間優先以識別碼、方向及站序配對。實測臺北 262 的 ETA 不含 SubRouteUID、StopSequence，因此缺欄位時改檢查整份站序：只有 RouteUID＋Direction＋StopUID 唯一、且 ETA 也唯一時才允許配對。多支線共用站或迴圈重複站無法區分時仍顯示「暫無預估」，不使用站名相似度猜測。

保留 StopStatus，區分尚未發車、交管不停靠、末班車已過及今日未營運。沒有預估時間不等於未行駛。畫面顯示本機取得時間；分鐘數是取得當下的快照，不會自行倒數。更新失敗保留舊資料與取得時間，並顯示錯誤訊息。

TDX 來源本身也可能存在更新延遲與空值，可參閱 [TDX 公車動態資料使用注意事項](https://motc-ptx.gitbook.io/tdx-zi-liao-shi-yong-kui-hua-bao-dian/data_notice/public_transportation_data/bus_dynamic_data)。

## 分層與驗證

- `data/models/`：資料欄位、站序及 ETA 配對。
- `data/services/`：認證、限流、網路與 repository 快取。
- `features/`：畫面及本次使用期間的收藏。
- `shared/widgets/`：共用的安全錯誤訊息與重試介面。

```sh
fvm flutter analyze --no-pub
fvm flutter test --no-pub
```

測試使用 MockClient 與可注入時間，不需要金鑰，也不消耗真實 TDX 用量。涵蓋滾動視窗、429 冷卻、快取到期、併發合併、城市與 UID、迴圈站牌、空值狀態、導覽、手動搜尋及刷新時離開畫面。
